# 🌱 새싹 레이더 (saessak-radar)

[디지털새싹](https://newsac.kosac.re.kr/) 프로그램 목록을 주기적으로 확인해서
**① 감시 조건에 맞는 새 프로그램 등록**, **② "모집 예정 → 모집 중" 상태 전환**을 감지하면
**텔레그램으로 알림**을 보내는 감시 앱입니다.

목록이 JavaScript로 렌더링되기 때문에 **Playwright(headless Chromium)** 로 읽습니다.

---

## 기능

- 10분(설정 가능) 간격으로 프로그램 목록 자동 수집
- 감시 조건(유형/권역/학교급/상태/교육대상) 매칭
- 신규 등록 → 🟡 `[새 프로그램]`, 모집 시작/전환 → 🔴 `[모집 시작]` 텔레그램 알림
- 같은 프로그램+상태로는 중복 알림 없음
- 수집 3회 연속 실패 시 `⚠️ 수집 실패 중` 경보 1회
- 웹 대시보드: 감시 상태 / 조건 일치 수 / 오늘 알림 수 / 최근 감지 로그 20건 / "즉시 확인" 버튼
- 설정 페이지에서 감시 조건 체크박스로 변경 → 다음 주기부터 적용
- **클릭 이동**: 텔레그램 알림에 `🔗 신청 페이지 열기` 인라인 버튼, 브라우저 알림 클릭 시 상세페이지 새 탭, 대시보드 로그 줄 클릭 시 상세페이지 새 탭
- **알림 리허설**: 대시보드 `테스트 알림 보내기` 버튼(`POST /api/test-alert`)으로 가짜 프로그램 1건을 실제 발송 경로(브라우저+텔레그램, 인라인 버튼 포함)에 태워 점검. 로그에 `test`로만 남고 오늘 알림 카운트·조건 일치 수·감시 스냅샷에는 미반영

Node.js · Express · Playwright(chromium) · node-cron · JSON 파일 저장

## 로컬 실행

```bash
npm install
npx playwright install chromium
cp .env.example .env   # 토큰/챗ID 채우기 (없어도 실행은 됨, 콘솔에만 출력)
npm start
```

- 브라우저에서 http://localhost:3000 접속
- **"지금 즉시 확인"** 버튼을 눌러 1회 수집 실행 → 콘솔에 `카드 N개 수집` 로그로 몇 개 잡히는지 확인
- 카드가 0개면 셀렉터/렌더링 문제 (에러 처리되어 diff는 스킵됨)

환경변수:

| 변수 | 설명 |
|------|------|
| `TELEGRAM_BOT_TOKEN` | 텔레그램 봇 토큰 |
| `TELEGRAM_CHAT_ID` | 알림 받을 채팅 ID |
| `DATA_DIR` | 상태 저장 경로 (비우면 `./data`) |
| `ADMIN_PASSWORD` | 설정/알림 보호용 관리자 비밀번호 (미설정 시 보호 없음) |
| `SEASON_YEAR` | 수집 대상 시즌 연도 (비우면 `2026`) — 사이트 목록 API 의 `season` 파라미터 |

> `.env` 파일은 서버 시작 시 자동 로드된다(이미 설정된 환경변수는 덮어쓰지 않음). 없으면 조용히 스킵.

### 기관 평가

설정 페이지의 **🏢 기관 평가** 섹션에서 운영기관 56곳을 직접 평가한다.

- 목록 시드: `src/institutions.seed.json` (레포). 기관이 늘면 이 파일에만 추가하면 된다
- 평가 저장: `DATA_DIR/institutions.json` (볼륨) — 재배포해도 유지된다. 시드 + 저장본을 병합해서 읽는다
- 평가 항목: 강사구성(6단계) · 강사료(초과/평균/이하) · 운영 편의(편함/보통/까다로움) ·
  교구(있음/없음) · 연수(참고) · 간식(2번+/1번/안줌) · ❤️ 승인 잘해줌(참고) ·
  종합판정(강력추천/추천/비추천) · 신청결과 메모 · 자유 메모
- **강사구성 0 = 신청 대상 제외** → 종합판정이 서버에서 `no`(비추천)로 고정된다
- 한 항목이라도 채우면 '평가완료'로 본다(별도 플래그를 관리하지 않음)

**강사구성 6단계**(`STAFF_STEPS`) — 단계 자체가 곧 배점이다(최대 50):
주+보조+안전 모두 학교 `50` · 주+보조 학교 `48` · 주+보조 학교, 안전만 외부 `45` ·
주강사만 학교 `40` · 보조강사만 학교 `30` · 신청 대상 제외 `0`.

**종합점수(0~100)** 는 저장하지 않고 읽을 때 계산한다(`storage.scoreOf`). 가중치는 `SCORE_WEIGHTS`
한 곳에만 있다 — 강사구성 50(단계 점수) · 강사료 20/18/15 · 운영 편의 10/9/8 ·
교구 10/8 · 간식 10/9/8, **합계 100**. 안 채운 항목은 0점, 아예 미평가면 `null`(랭킹 맨 아래),
**강사구성 0이면 무조건 0점**.

**종합판정·연수·하트는 점수에 반영하지 않는다** — 판정은 사람이 내리는 결론이고, 연수·하트는
참고 항목이라 점수에 섞으면 같은 근거를 두 번 세게 된다. 연수 선택지는 라이브 / 동영상 /
초반 라이브→후반 동영상이며, 예전에 저장된 `online`/`offline` 값도 계속 허용해 사용자가 다시
고르기 전까지 사라지지 않는다. 리스트는 종합점수·강사구성·가나다·평가완료 우선으로 정렬할 수 있다.

**구 배점 체계 이관**(멱등, 서버 시작 시 `migrate.js` → `storage.migrateInstitutionsFile`,
읽을 때도 `getInstitutions` 에서 한 번 더 통과):
강사구성 `5→50 · 4.5→45 · 4→40 · 3→30 · 0→0` · 강사료 `good→over · poor→under` ·
간식 `yes→once · unknown→null` · 종합판정 `redo→strong · skip→no`.
구 값과 신 값이 겹치지 않아 몇 번을 다시 돌려도 결과가 같다.

**플래너에 표시**(`showRatings`, 기본 OFF)가 마스터 스위치다. 켜면 플래너·최근 감지 카드의
업체명 앞에 **판정 문구 배지 · 종합점수 · ❤️** 순으로 표식이 붙고, 어떤 표식을 붙일지는 개별로 고른다 —
`showVerdict`(강력추천/추천/비추천 배지) · `showScore`(종합점수 N점) · `showHeart`(❤️) 기본 ON,
`dimSkip`(비추천 기관 카드 흐리게, `opacity .65`) 기본 OFF. 마스터가 OFF면 개별 설정과 무관하게
전부 숨김이다. 미평가·매칭 실패 기관은 표식이 없고, 텔레그램 메시지는 이 설정의 영향을 받지 않는다.

카드에는 **강사구성 원점수(★N)를 따로 띄우지 않는다** — 종합점수에 이미 들어가 있어 같은 근거를
두 번 보여주게 되기 때문이다. 강사구성 단계는 설정 화면의 기관 목록 요약(★N)과 표식 툴팁에서 본다.
구 옵션 키 `showStaffScore` 는 폐지됐고 서버 시작 시 `storage.pruneSettings` 가 저장본에서 지운다.

API: `GET /api/institutions` · `POST /api/institutions/:name` (둘 다 설정 잠금 시 인증 필요)

### 조건 판정 방식

감시 조건 5개 카테고리는 **모두 합집합(OR)** 이다 — 체크한 값 중 **하나라도** 카드에 있으면 통과.

| 카테고리 | 판정 | 비고 |
|---|---|---|
| 프로그램 유형 | OR | 카드 값이 단일(방문형/집합형) |
| 운영권역 | OR | 카드가 여러 권역을 가질 수 있음 |
| 학교급 | OR | 카드가 여러 학교급을 가질 수 있음 |
| 모집상태 | OR | 카드 값이 단일 |
| 교육대상 | OR | 카드가 여러 대상을 가질 수 있음 · `미분류` 체크 시 신설 라벨도 통과 |

- **여러 개 체크 = 조건이 넓어짐** (좁아지는 게 아님). 설정 UI 각 카드에 이 문구를 표시한다.
- **카테고리끼리는 AND** — 5개를 전부 통과해야 최종 통과
- 한 카테고리를 **전부 해제하면 조건 없음**(그 항목 전체 통과)
- **프로그램 수준은 감시 조건에서 제외** — 요청에 `levelCode` 를 보내지 않아 기본·특화·AI특화가 전부 통과한다.
  수준은 프로그램당 하나뿐이라 여러 개를 AND 로 걸면 결과가 0건이 되기 때문.
  향후 설정에 노출한다면 **단일 선택(라디오) + 기본값 '전체'** 로 만들 것.

참고 코드표 (사이트 필터 UI 실측):

| 그룹 | 코드 |
|---|---|
| 프로그램 수준 | `C0401` 기본 · `C0402` 특화 · `C0403` AI특화 |
| 프로그램 소양 | `C0301` 컴퓨팅 사고력 · `C0302` 인공지능 소양 · `C0303` 디지털 리터러시 · `C0304` 데이터 소양 |
| 학교급 | `G007` 초등학교 · `G008` 중학교 · `G009` 고등학교 |
| 모집상태 | `C1101` 모집 예정 · `C1102` 모집 중 · `C1103` 모집 완료 |

### 수집 API 스펙 (2026-08 변경)

목록 API `GET /newsac/api/v1/programs/user` 는 `season`(시즌 연도) + `version`(=`v2`) 를
함께 받도록 바뀌었다. 두 값 없이 호출하면 "인증 필요" 로 거절될 수 있어 항상 붙인다.

- `season` : `SEASON_YEAR` 환경변수 (기본 `2026`) — 연도가 바뀌면 변수만 교체
- `version`: `v2` 고정 — `v2` 는 사이트 화면과 동일한 목록(지난 시즌 잔여분 제외)을 준다
- `size=100` + `page` 순회로 전 페이지 수집 → 조건 일치 누락 방지
- 권역/학교급/교육대상 필터는 **서버에 보내지 않는다**. 전량을 받아 `watcher` 가
  설정으로 거르기 때문에 설정 변경 시 재수집이 필요 없고, 신설 분류도 '미분류'로 잡힌다
- 로그인 쿠키 불필요(공개 데이터). 추가 헤더도 `Accept: application/json` 하나면 충분
- 상세 API `GET /newsac/api/v1/programs/{id}` 는 아직 두 파라미터 없이도 동일 응답이지만,
  같은 변경이 오면 바로 깨지므로 동일하게 붙여 호출한다

교육대상 코드(코드그룹 `G006`) — `src/classify.js` 단일 소스:

| 코드 | 라벨 |

| `C0602` | 사회적 배려형(도서벽지) |

### 🔒 설정 비밀번호 보호 (`ADMIN_PASSWORD`)

`ADMIN_PASSWORD` 를 설정하면 **감시 조건 설정과 알림 발송**이 비밀번호로 보호된다. 외부 라이브러리 없이 Node 내장 `crypto` 만 사용한다.

- **보호 대상**: `GET /settings`, `POST /api/settings`, `POST /api/test-alert`, `POST /api/check-now`
- **공개 유지**: 대시보드 `/`, `/health` (열람은 로그인 없이 가능)
- **동작**: 비밀번호 입력(`/auth`)이 일치하면 HMAC 서명 쿠키(만료 30일, `HttpOnly`)를 발급하고, 서명 검증 미들웨어가 보호 라우트를 감싼다. 비밀번호 비교는 `crypto.timingSafeEqual` 사용. 비밀번호를 바꾸면 기존 쿠키는 자동 무효화된다.
- **미설정 시**: 보호가 완전히 꺼져 지금처럼 로그인 없이 사용 (로컬 개발 편의).
- 대시보드의 `⚙️ 감시 조건 설정` 버튼은 그대로 두되, 미인증 상태로 누르면 비밀번호 페이지를 경유한다.

```bash
# .env 예시
ADMIN_PASSWORD=원하는비밀번호
```

Railway 등 배포 환경에서는 **Variables** 탭에 `ADMIN_PASSWORD` 를 추가한다.

## 텔레그램 봇 만들기 (요약)

1. 텔레그램에서 **@BotFather** 검색 → `/newbot` → 이름/username 지정 → **봇 토큰** 발급
2. 방금 만든 봇에게 아무 메시지나 1개 전송 (봇이 나에게 말 걸 수 있게)
3. **@userinfobot** 에게 말 걸어 내 **chat id**(숫자) 확인
   (그룹으로 받으려면 봇을 그룹에 초대 후 그룹 chat id 사용)
4. `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` 에 각각 입력

## Railway 배포 순서

1. 이 저장소를 GitHub에 push
2. [Railway](https://railway.app) → **New Project → Deploy from GitHub repo** → `saessak-radar` 선택
3. Railway가 **Dockerfile을 자동 인식**해서 빌드 (Playwright 베이스 이미지라 크로뮴 포함)
4. **Variables** 탭에서 환경변수 2개 등록:
   - `TELEGRAM_BOT_TOKEN`
   - `TELEGRAM_CHAT_ID`
5. **Volume** 추가 → 마운트 경로를 `/data` 로 설정 → 변수에 `DATA_DIR=/data` 추가
   (재배포/재시작해도 감시 스냅샷과 로그가 유지됨)
6. Deploy 완료 후 도메인 접속 → 대시보드 확인, "즉시 확인"으로 수집 테스트

> Volume을 붙이지 않으면 재시작 때마다 state가 초기화되어, 배포 직후 기존 프로그램들이
> "신규"로 잡혀 알림이 몰려올 수 있습니다. **`/data` Volume 권장.**

### ⚠️ Railway 절전(App Sleeping)은 반드시 꺼야 한다

이 앱은 **웹 요청이 없어도 스스로 도는 감시 루프**가 본체다. Railway 의 App Sleeping
(Serverless)이 켜져 있으면 인바운드 요청이 없을 때 컨테이너가 잠들고, **잠든 동안에는
타이머가 서지 않아 감시가 통째로 멈춘다.** 대시보드를 열면 그제야 깨어나므로,
"내가 볼 때는 늘 정상인데 알림만 안 온다" 는 형태로 나타난다.

1. **(정답) 절전 끄기** — Railway → 해당 Service → **Settings → Serverless / App Sleeping** 을 **OFF**.
2. **(보조) 자체 keep-alive** — 앱이 자기 공개 URL 의 `/health` 를 5분마다 때려 유휴 타이머를
   계속 초기화한다. `RAILWAY_PUBLIC_DOMAIN` 이 있으면 자동 동작하고, 없으면 `KEEPALIVE_URL`
   변수로 지정한다. **한계: 이미 잠든 뒤에는 스스로 깨우지 못한다.**
3. **(권장) 외부 모니터** — UptimeRobot·cron-job.org 등에서 5분 간격으로 `/health` 를 호출.
   밖에서 두드리는 것이라 잠들어도 깨우고, 잠드는 것 자체를 막는다.
   **알림까지 받으려면 `/health/watch`** 를 걸어 둔다(아래).

## 감시가 멈추지 않게 하는 장치

2026-08-18 에 감시가 2시간 멈춘 적이 있다. 원인은 **에러가 아니라 정지(hang)** 였다.
스케줄러는 "수집이 끝난 뒤"에 다음 주기를 예약하는 자기예약 구조인데,
사이트 응답이 오지 않아 `page.evaluate` 안의 `fetch` 가 영원히 매달렸고 —
그 줄에 타임아웃이 없어서 — **다음 주기를 예약하는 코드에 영영 도달하지 못했다.**
(에러는 원래도 `try/catch` 로 잡고 있었다. 잡을 예외 자체가 발생하지 않은 것이 함정이었다.)

지금은 여섯 겹으로 막는다. **안쪽이 먼저 끊겨야 바깥이 헛돌지 않는다** —
아래 순서가 이 설계의 전부다.

```
페이지 fetch(20초/건) < evaluate(60초) < 스크래퍼 1회(90초)
    < 사이클(4분) < 죽은 락 판정(5분) < 워치독(30분)
```

| 겹 | 장치 | 값 | 하는 일 |
|---|---|---|---|
| 1 | 페이지 안 `fetch` 타임아웃 | 20초/건 | 사이트가 응답을 안 주면 그 요청만 끊는다 |
| 2 | `page.evaluate` 상한 | 60초 | 매달린 수집을 예외로 끝낸다 |
| 3 | **스크래퍼 1회 상한** `SCRAPE_TIMEOUT_MS` | **90초** | 기동·접속·수집을 통틀어. 넘기면 예외로 끝나고 `finally` 가 컨텍스트·브라우저를 닫는다 |
| 4 | 사이클 상한 `CYCLE_TIMEOUT_MIN` | 4분 | 그래도 안 끝나면 사이클을 강제 종료. **예약은 `finally` 에서 하므로 무조건 다음 주기가 잡힌다** |
| 5 | **죽은 락 판정** `STALE_LOCK_MIN` | **5분** | 다음 수집이 시작될 때, '진행 중' 플래그가 이만큼 잡혀 있으면 죽은 것으로 보고 강제 해제 후 실행 |
| 6 | 워치독 `WATCHDOG_STALL_MIN` | 30분 | 활동이 끊기면 락을 풀고 스케줄을 새로 잡고 즉시 1회 수집 + 텔레그램 경보 |

- **죽은 락 판정(5겹)이 이번에 추가된 핵심이다.** 워치독만으로는 첫 30분을 못 살린다.
  플래그가 걸린 채 멈추면 그 사이 모든 수집이 "이미 진행 중" 으로 거부됐다(6시간 정지).
  이제는 다음 수집 시도가 스스로 판단해서 푼다.
- **`STALE_LOCK` 은 반드시 `CYCLE_TIMEOUT` 보다 커야 한다.** 짧으면 살아 있는 수집을
  죽은 것으로 오인해 크로뮴이 겹쳐 뜬다(`spawn EAGAIN`). 설정을 잘못 줘도
  `max(설정값, 사이클상한 + 1분)` 으로 보정한다.
- 워치독의 실제 임계값은 **`max(30분, 수집간격 × 3)`** 이다. 수집 간격을 30분 이상으로
  잡아도 오발동해서 수집을 덧돌리지 않는다.
- 브라우저는 **수집 1회마다 새로 띄우고 끝나면 완전히 종료**한다(`runInBrowser`).
  재사용하면 세션·메모리가 쌓이고, 한 번 이상해진 인스턴스가 이후 모든 주기를 오염시킨다.
  컨텍스트·브라우저 종료는 타임아웃으로 빠져나갈 때도 `finally` 를 지난다.

### 실패가 쌓일 때

- 상태바가 `수집 실패 N회 연속` 으로 바뀐다(빨강). 연속 실패는 성공하면 0 으로 돌아간다.
- `/health/watch` 는 **멈춘 경우(`stalled`)뿐 아니라 3회 연속 실패(`failing`)에도 503** 이다.
  밖에서 보면 둘 다 '알림이 안 온다' 로 같기 때문이다.
- 죽은 락을 강제로 푼 횟수(`staleUnlocks`)가 쌓이면 무언가 반복해서 멈추고 있다는 뜻이다.

### 하트비트 (`DATA_DIR/heartbeat.json`)

매 사이클마다 시작·종료를 파일에 남긴다. 볼륨에 있으므로 **재배포·재시작해도 유지**되고,
부팅 시 되읽어서 상태바가 "확인 전" 으로 리셋되지 않는다.

```json
{ "lastStartAt": "...", "lastFinishAt": "...", "lastOk": true,
  "lastError": null, "lastReason": "cron", "lastMs": 4210, "restarts": 0 }
```

상태바의 **"마지막 확인"은 `lastFinishAt`(끝난 시각)** 이다. 시작 시각을 쓰면 매달려 죽은
사이클이 한동안 "방금 확인" 으로 보여 사고를 놓친다. `restarts` 는 워치독이 되살린 누적 횟수로,
0 이 아니면 뭔가 반복해서 멈추고 있다는 뜻이다.

### 상태 확인용 엔드포인트

| 주소 | 인증 | 용도 |
|---|---|---|
| `/health` | 없음 | 프로세스 생존만 확인. **항상 200** (keep-alive·절전방지 핑 대상) |
| `/health/watch` | 없음 | **감시 루프가 실제로 도는지.** 멈춰 있으면 **503** → 외부 모니터 알림용 |
| `/api/summary` | 없음 | `status.lastCheckedAt`·`staleMinutes`·`watchdogRestarts` 등 상세 |

```bash
curl -s https://<도메인>/health/watch
# {"ok":true,"lastCheckedAt":"...","idleMinutes":3,"stallMinutes":30,
#  "collecting":false,"watchdogRestarts":0}
```
